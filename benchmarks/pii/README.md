# PII detection benchmark

**Current result: 84.3% recall, 94.2% precision** over 2,076 labelled spans in
760 documents. Full tables in [results.md](results.md), regenerated by the
commands below.

```bash
make bench-pii                              # score and print
python benchmarks/pii/run.py --write        # score and update results.md
python benchmarks/pii/generate_corpus.py    # rebuild corpus.jsonl (seeded)
```

Nothing here runs in the test suite, nothing downloads anything, and nothing
needs an API key.

## Why this exists

`wardhook-guardrails` claims to detect personal data. The first question a
compliance reviewer asks is what the false-negative rate is, and until this
existed the honest answer was that nobody had measured it. Prose about
limitations is worth having — [the design doc](../../docs/packages/guardrails.md#limitations)
has it — but prose is not a number a reviewer can cite, argue with, or check.

**The number is published whatever it says.** A documented recall of 0.84 is a
far stronger position than no figure at all, because it lets a reader decide
whether that is good enough for their use. Tuning the corpus until the detector
looked better would destroy the only asset this project actually has, which is
that its claims survive being checked.

## Method

**The corpus is generated from real-world identifier formats, never from
Wardhook's own regexes.** This is the load-bearing decision. A corpus built out
of the patterns under test would score near 1.0 and measure nothing at all.
Every generator in [generate_corpus.py](generate_corpus.py) encodes how an
identifier is actually written, including the variants a pattern may not
anticipate: a US SSN with and without dashes, a date of birth in British, ISO
and long-hand forms, an IBAN grouped in fours as a bank prints it, a Medicare
beneficiary identifier both grouped and ungrouped.

One deliberate departure from realism, in one place: generated API keys carry a
bare `sk_`/`pk_`/`rk_` prefix with no `live`/`test`/`proj` segment. With those
segments the strings are indistinguishable from real Stripe and OpenAI
credentials — secret scanners block the file, nobody can safely grep past it,
and no reader can tell the values are fabricated. The rule under test accepts
the bare prefixes, so it is still exercised at a realistic length, and
`API_KEY` scores identically either way.

Checksums are computed from the public specifications — Luhn for cards, mod-97
for IBANs, modulus-11 for NHS numbers — so values are format-valid and the
validators are genuinely exercised. Every value is fabricated; names, streets,
domains, phone numbers and IP addresses come from documentation placeholders and
reserved ranges (RFC 5737, RFC 1918, NANP 555-01xx, Ofcom 020 7946 0xxx).

760 documents: 150 per pack of short correspondence carrying two to five
identifiers in natural prose, plus 40 per pack of **clean documents** containing
near-misses — version strings, order numbers, page ranges, section references —
which a detector must leave alone. The generator is seeded, so `corpus.jsonl` is
reproducible byte for byte and is committed so a reader can inspect exactly what
was measured without running anything.

The runner verifies that every labelled span still lines up with its text before
scoring, and refuses to score a corpus where it does not. A misaligned corpus
would produce numbers that look plausible and mean nothing.

### What each figure means

A redactor's job is to cover the sensitive substring, so the headline **recall**
asks whether a labelled span was fully covered by *some* detection, whichever
rule fired. An NHS number caught by the phone rule is mislabelled but not
leaked. **Recall (typed)** additionally requires the right entity name, because
a wrong label degrades the audit trail even when the redaction worked.

**Precision** counts a detection as correct if it landed on labelled data at
all. A detection overlapping nothing labelled is a false positive: it redacts
something that was not personal data, and that cost lands on whoever reads the
text afterwards. Detections landing on real PII under the wrong name are
reported separately rather than folded into either figure.

## What these numbers do not support

- **The corpus is ours.** It measures the rules against formats we thought to
  write down. It is a floor on false negatives, not a ceiling: a format nobody
  here anticipated is absent from both the patterns and the corpus, and will not
  show up as a miss. An independent public corpus would be a stronger test and
  is the obvious next step.
- **English only, and mostly UK/US.** Non-English text and non-Anglophone
  address, phone and identifier conventions are not represented, and the design
  doc already records that coverage there is weak.
- **Prose is synthetic.** Sentences are assembled from templates. Real tickets
  contain typos, line breaks mid-identifier, OCR noise and pasted tables, none
  of which are here.
- **It says nothing about injection detection or RBAC.** This measures the
  entity rules only.
- **A per-entity figure over ~40 spans is indicative, not tight.** Treat the
  headline and per-pack numbers as the reliable ones.

## What the result actually says

The rules are strong on structured identifiers with a distinctive prefix or a
checksum — `CREDIT_CARD`, `NHS_NUMBER`, `IBAN` when unspaced, `AWS_ACCESS_KEY`,
`VIN`, and the domain-specific references — and weak wherever one real-world
identifier has several written forms and the pattern encodes one of them:

- `DATE_OF_BIRTH` (37%) matches `DD/MM/YYYY` and `DD-MM-YYYY` only. ISO
  `1982-03-14` and long-hand `March 14, 1982` are both missed.
- `POSTAL_ADDRESS` (38%) misses anything led by a flat or apartment.
- `MEDICARE_ID` (43%) misses the grouped form printed on the card itself.
- `IBAN` (49%) misses the spaced form printed on statements.
- `US_SSN` (53%) requires the dashes.
- `UK_SORT_CODE` (54%) requires hyphens, not spaces.

Two precision figures are worth the same attention. `SWIFT_BIC` (38%) fires on
ordinary capitalised words near "wire" or "transfer", and `IP_ADDRESS` (70%)
fires on dotted version strings such as `10.2.14.3`. Both over-redact.

These are specific, reproducible, and fixable. Fixing them is separate work,
deliberately: this number was published before anything was tuned, so the next
result can be compared against a figure nobody had an incentive to flatter.
